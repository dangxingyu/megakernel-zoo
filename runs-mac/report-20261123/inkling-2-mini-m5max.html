TL;DR

Inkling-2-Mini is a 26 B mixture-of-experts model meant for devices, shipped with NVFP4 experts and a DSpark draft head. On an M5 Max (40-core GPU, 48 GB), two six-hour runs of Claude Fable 5.2 wrote an engine in MLX and run-time Metal that decodes one sequence at 8.1 ms per token on the synthetic workload and 5.1 ms on natural text (123 and 194 tokens/s). That is 1.70× and 1.62× the fastest engine we found for this model on a Mac (oMLX on its own 4-bit requantization, with DSpark), 3.7× mlx-lm on the same weights, and 3.1× llama.cpp on a Q4_K_M GGUF.Inkling-2-Mini 是一个面向端侧的 26 B MoE 模型，发布时 experts 是 NVFP4，并带一个 DSpark draft head。在一台 M5 Max（40 核 GPU，48 GB）上，Claude Fable 5.2 跑了两轮、每轮六小时，用 MLX 和运行时编译的 Metal 写出一个 engine。它单序列解码 synthetic workload 每 token 8.1 ms，自然文本 5.1 ms（123 和 194 tokens/s），是我们在 Mac 上找到的最快 engine（oMLX 在它自己的 4-bit 重量化权重上加 DSpark）的 1.70× 和 1.62×，是同样权重下 mlx-lm 的 3.7×，是 llama.cpp 跑 Q4_K_M GGUF 的 3.1×。

Exact, on the checkpoint's formats. Every token the engine returns is the token its own one-token greedy step would choose; the evaluator checks this on every sequence. The weights are the stored NVFP4, MXFP8 and BF16 values; the dense BF16 matrices are read through a lossless 12-bit code that decodes to the identical bits. The second run gained 10% on synthetic text from that code, a draft depth chosen by a cost model, and expert kernels that read each expert once per pass.结果是精确的，权重是 checkpoint 自己的格式。 engine 返回的每个 token 都等于它自己一次走一个 token 的 greedy step 会选的那个，evaluator 在每条序列上逐一检查。权重是存储的 NVFP4、MXFP8、BF16 原值；dense 的 BF16 矩阵通过一种无损 12-bit 编码读取，解码出来逐位相同。第二轮在 synthetic 上又快了 10%，来自三处：这个编码、由代价模型决定的 draft 深度、以及每个 pass 每个 expert 只读一次的 expert kernel。

The error. Every BF16 engine sits about 0.025 (median relative L2 of the logits) from the float32 reference. 83% of that is expert routing: in 39% of (token, layer) pairs the 8th and 9th expert scores are within BF16 noise and the choice flips. With float32's routes forced, the error falls to 0.0045. The engine is served by mkserve behind the OpenAI, Anthropic and Ollama APIs and passes all twelve of its serving checks. Prompts are prefilled in wide passes: a 1,630-token prompt gets its first token after 1.2 s, down from 6.3 s. A prefix cache starts the next turn of a chat after 0.2 s, the context goes to 32,768 tokens, and sampling runs through the same exact draft-and-verify at greedy speed.误差。 所有 BF16 engine 与 float32 reference 之间都差 0.025 左右（logits 相对 L2 误差的中位数）。其中 83% 来自 expert 路由：39% 的 (token, layer) 上，第 8 和第 9 名 expert 的分数差在 BF16 噪声以内，选择会翻转。强制使用 float32 的路由后，误差降到 0.0045。engine 通过 mkserve 以 OpenAI、Anthropic、Ollama 三种 API 对外服务，12 项部署检查全部通过。prompt 现在用宽 pass 预填充：1,630-token 的 prompt 首 token 从 6.3 s 降到 1.2 s。prefix cache 让对话的下一轮 0.2 s 就开始，上下文扩到 32,768 token，sampling 走同一套精确的 draft-and-verify，速度与 greedy 相当。

Setup设定

In the B200 post the agent wrote one CUDA megakernel per model. A Mac has no offline Metal compiler without Xcode and no grid-wide barrier, so the unit here is a pass: K consecutive positions of one sequence through the whole model, built from our own Metal kernels (through mx.fast.metal_kernel) and traced once per K with mx.compile. No library model code runs in the timed path: not mlx-lm, oMLX, llama.cpp or transformers.在 B200 那篇里，agent 为每个模型写一个 CUDA megakernel。Mac 上没有 Xcode 就没有离线 Metal 编译器，也没有全网格同步，所以这里的基本单元是一个 pass：一条序列连续 K 个位置走完整个模型，由我们自己的 Metal kernel（通过 mx.fast.metal_kernel）组成，每种 K 用 mx.compile trace 一次。计时路径里不跑任何库的模型代码：没有 mlx-lm、oMLX、llama.cpp 或 transformers。

The track is C, exact speculative decoding. The engine drafts tokens with the checkpoint's DSpark head (mtp.safetensors) and with n-gram copies from the prompt and its own output, then verifies them in one K-row pass. Every row of that pass must have the bits the one-token step would give it, so every per-row sum keeps an order that does not depend on K. Speculation changes the speed, never the text.这次是 track C：精确的 speculative decoding。engine 用 checkpoint 的 DSpark head（mtp.safetensors）以及从 prompt 和自身输出里做的 n-gram copy 来起草 token，再用一个 K 行的 pass 一次验证。这个 pass 的每一行都必须和单 token step 给出的 bits 完全一样，所以每一行的每个求和，顺序都不能随 K 变化。speculation 只改变速度，不改变文本。

The workload is the one from the post: a 64-token prompt, 1,024 greedy new tokens, one sequence, served over HTTP. The rate counts tokens received, so a verify pass that commits five tokens counts five. The headline is the synthetic prompts; natural text (prose, Python source, word problems) is reported next to it. Every submission passes the same gates before it is timed:workload 与博客相同：64-token prompt，生成 1,024 个 greedy token，单条序列，通过 HTTP 服务。速率按收到的 token 数计，一个提交了 5 个 token 的验证 pass 算 5 个。主指标是 synthetic prompts，自然文本（散文、Python 代码、数学应用题）一并报告。每次提交在计时前都要通过同样的 gate：

Decode speed解码速度

We measured every engine we could get to run this model on the same Mac, through the same client: mlx-lm on the checkpoint as stored, oMLX on its published 4-bit requantization with and without DSpark, llama.cpp on a Q4_K_M GGUF with and without a DSpark pull request, and Ollama.我们在同一台 Mac 上、用同一个 client，测了所有能跑这个模型的 engine：mlx-lm 跑原始 checkpoint，oMLX 跑它发布的 4-bit 重量化版本（加和不加 DSpark），llama.cpp 跑 Q4_K_M GGUF（加和不加一个 DSpark 的 pull request），以及 Ollama。

Against the fastest general engine, oMLX with DSpark at 13.8 / 8.3 ms per token, the final engine is 1.70× on synthetic prompts and 1.62× on natural text. oMLX reads fewer bytes, since it requantized the model to 4 bits; against mlx-lm on the same weights as ours the factor is 3.7× and 5.9×. With the copy proposals switched off, so that every draft comes from the DSpark head, the engine runs at 8.8 / 6.8 ms (1.56× / 1.21× oMLX + DSpark): the copy proposals are worth 8% on synthetic text and 25% on natural text, where continuations repeat more.对比最快的通用 engine（oMLX 加 DSpark，每 token 13.8 / 8.3 ms），最终 engine 在 synthetic 上是 1.70×，在自然文本上是 1.62×。oMLX 把模型重量化到了 4 bit，读的字节更少；和同样权重的 mlx-lm 比，倍数是 3.7× 和 5.9×。关掉 copy proposals、只让 DSpark head 起草时，engine 是 8.8 / 6.8 ms（oMLX + DSpark 的 1.56× / 1.21×）：copy proposals 在 synthetic 上值 8%，在自然文本上值 25%，因为自然文本的续写更容易重复。

Where the time goes depends on the text. On prose, a cycle takes about 19.5 ms: a verify pass of about 2.3 rows (16.3 ms), the draft (2.4 ms) and 0.5 ms between cycles, and commits about 1.75 tokens. The verify pass reads 2.1 GB of 12-bit dense codes, 0.46 GB of an 8-bit unembedding copy for the exact-argmax short list, and about 1.5 GB of experts per row, at 450–530 GB/s; it is near the memory roofline. On text that repeats itself (half of the natural workload's time) the engine verifies 16-row copy proposals at about 3.1 ms per token, and there it is bound by arithmetic: the experts of a 16-row pass are 81 G multiply-adds in 28.5 ms.时间花在哪里取决于文本。在散文上，一个 cycle 约 19.5 ms：约 2.3 行的验证 pass（16.3 ms）、draft（2.4 ms）、cycle 之间 0.5 ms，提交约 1.75 个 token。验证 pass 每行读 2.1 GB 的 12-bit dense 编码、0.46 GB 用于精确 argmax 候选短名单的 8-bit unembedding 副本，以及约 1.5 GB 的 experts，带宽 450–530 GB/s，已经接近内存 roofline。在会自我重复的文本上（占自然文本 workload 一半的时间），engine 验证 16 行的 copy proposals，每 token 约 3.1 ms，这时瓶颈是算力：16 行 pass 的 experts 是 81 G 次乘加，耗时 28.5 ms。

What moved the number哪些改动有效

The first run started from a plain MLX pass with no speculation (26.9 ms per token) and ended at 9.0 / 5.3 ms. The second run started from that engine, with a prompt that asked for changes to the algorithm (more tokens per pass, fewer bytes per token) rather than more kernel tuning, because the first run had found its passes near the memory roofline.第一轮从一个不带 speculation 的朴素 MLX pass 开始（每 token 26.9 ms），结束时到了 9.0 / 5.3 ms。第二轮从这个 engine 出发。由于第一轮已经发现 pass 接近内存 roofline，第二轮的 prompt 要求改算法（每个 pass 提交更多 token、每个 token 读更少字节），而不是继续调 kernel。

A 12-bit code for BF16 weights, again又一次：BF16 权重的 12-bit 编码

The dense BF16 matrices (attention projections, gates, output projections) are 2.6 GB of every pass. As in track B on the B200s, the agent measured that the weights of one row span few binades: with a per-row window of 16 exponents, 8.8 × 10−5 of the weights fall outside. It stores 4 weights in 6 bytes (sign and mantissa bytes, plus a 4-bit exponent offset each) and keeps the 19% of rows that have an outlier as plain BF16 in a side array, so the kernel has no escape branch. Each weight is rebuilt to its stored 16 bits before the same fma chain, so every sum keeps its order and its bits; the loader asserts the round trip. The two largest matrices went from 4.4 to 3.2 ms per one-row pass, and the decode keeps up with memory at 530 GB/s on the packed bytes.dense 的 BF16 矩阵（attention 投影、gate、输出投影）每个 pass 要读 2.6 GB。和 B200 上的 track B 一样，agent 测得同一行权重只跨很少几个 binade：按每行 16 个指数的窗口，只有 8.8 × 10−5 的权重落在窗口外。它把 4 个权重存成 6 个字节（符号和尾数的字节，加上每个权重 4 bit 的指数偏移），带离群值的那 19% 的行照旧以 BF16 存在一个旁路数组里，所以 kernel 里没有转义分支。每个权重先还原成存储的 16 bits，再进入同样的 fma 链，所以每个求和的顺序和 bits 都不变；loader 会断言往返一致。最大的两个矩阵在单行 pass 上从 4.4 ms 降到 3.2 ms，解码速度跟得上内存，压缩后的字节流达到 530 GB/s。

How deep to draftdraft 起草多深

A verify row costs about 2.5 ms on prose; a committed token is worth about 10. The engine keeps verifying rows while the calibrated probability that the whole prefix is accepted stays above the row's cost times the request's recent tokens per millisecond. The calibration is kept per request, P(accept | depth, bucket of the draft's probability) with a decay, because the head's probabilities mean different things on different text. This gained 5.3% on synthetic text and nothing on natural text, half of whose time is in copy passes the policy does not touch.在散文上，验证一行约花 2.5 ms，一个提交的 token 约值 10 ms。只要"整段前缀全被接受"的校准概率还高于"这一行的耗时 × 该请求最近每毫秒产出的 token 数"，engine 就继续加验证行。校准按请求分别维护，统计的是带衰减的 P(accept | 深度, draft 概率所在区间)，因为 head 给出的概率在不同文本上含义不同。这在 synthetic 上带来 5.3% 的提升，在自然文本上没有效果：自然文本有一半时间花在 copy pass 上，而这个策略不管 copy pass。

What we measured and dropped测过但放弃的

The second run's prompt listed five algorithmic directions. The agent ran the cheap measurement that decides each before building it:第二轮的 prompt 列了五个算法方向。agent 在动手实现之前，先为每个方向跑了能做出判断的低成本测量：

  • Token trees. Over 11 greedy continuations, DSpark's second-best first token is right at 1–5% of the anchors (12% on the hardest prose). Replaying the decode with a sibling row for it gains 0.0–0.3%. Not built.Token tree。 在 11 条 greedy 续写上，DSpark 的第二候选首 token 只在 1–5% 的锚点上是对的（最难的散文上 12%）。用一行兄弟节点回放解码，收益 0.0–0.3%。没有做。
  • Suffix-structure proposals. Matches shorter than 5 tokens are right 3–14% of the time unless the DSpark chain already says the same thing, and then they add nothing.Suffix 结构的候选。 短于 5 个 token 的匹配只有 3–14% 是对的；对的那些，DSpark 链本来就已经给出，加了也没用。
  • Lossless codes for the experts. NVFP4 codes carry 3.97 of their 4 bits, and the expert kernels are compute-bound from 3 rows up: decoding by arithmetic instead of a table is 60–90% slower.expert 的无损编码。 NVFP4 每个码本身就带 3.97 bit 信息（满分 4 bit），而且 expert kernel 从 3 行起就是算力瓶颈：用算术代替查表解码会慢 60–90%。
  • Fewer host round trips. Chaining the draft behind the verify pass cut syncs from 2–3 to 1 per cycle, worth about 1%: a sync costs about 0.2 ms here. Removing the remaining 0.5 ms of idle GPU per cycle would need a fixed row count, which loses about as much as it saves.更少的 host 往返。 把 draft 接在验证 pass 后面，每个 cycle 的同步从 2–3 次降到 1 次，约快 1%：这里一次同步只要 0.2 ms 左右。要去掉每个 cycle 剩下的 0.5 ms GPU 空闲，就得固定行数，而固定行数损失的和省下的差不多。
  • Copies from 8 matching tokens instead of 5. −0.9% in process, +0.8% / −0.6% in the evaluation. Reverted.copy 匹配长度从 5 改到 8。 进程内 −0.9%，评测中 +0.8% / −0.6%。已回退。

What limits the prose regime now is the draft head: its first token is right 60–70% of the time on prose and 98% on code and word problems. A better draft, not a faster pass, is the next large factor there.现在限制散文场景的是 draft head：它的首 token 在散文上只有 60–70% 是对的，在代码和应用题上是 98%。那里下一个大的提升来自更好的 draft，而不是更快的 pass。

Where the error comes from误差从哪来

Every BF16 implementation we have is about 0.025 from the float32 reference: the repository's BF16 path (0.027), our engine (0.024) and mlx-lm (0.026). We took the reference apart to see why.我们手上所有 BF16 实现与 float32 reference 都差 0.025 左右：仓库里的 BF16 路径（0.027）、我们的 engine（0.024）、mlx-lm（0.026）。我们把 reference 拆开来看原因。

Inkling-2-Mini routes each token to 8 experts, and the 8th and 9th scores are often within BF16 noise of each other. A flipped choice also changes the K/V history every later position attends to, which is why the error grows with position (0.033 median at long positions against 0.025 in the first 128). Forcing float32's choices cuts the median 6× and the p99 12×. The remaining 0.0045 is spread over the model: rounding only one family of operations at a time, with float32's routes, gives attention 0.0024, the attention residuals 0.0023, the MoE 0.0023, the norms 0.0014, the short convolutions 0.0013 and the loop's message gates 0.0005. These add in quadrature to 0.0045, against 0.0043 with all of them rounded together.Inkling-2-Mini 给每个 token 选 8 个 expert，而第 8 名和第 9 名的分数经常在 BF16 噪声以内。一次选择翻转还会改变后面所有位置都要 attend 的 K/V 历史，所以误差随位置增大（长位置中位数 0.033，前 128 个位置是 0.025）。强制使用 float32 的选择后，中位数降了 6 倍，p99 降了 12 倍。剩下的 0.0045 分散在整个模型里：在使用 float32 路由的前提下，一次只让一类运算按 BF16 舍入，结果是 attention 0.0024、attention residual 0.0023、MoE 0.0023、norm 0.0014、short convolution 0.0013、loop 的 message gate 0.0005。这些按平方和开方合起来是 0.0045，全部一起舍入时实测是 0.0043。

Two consequences. The gate's limits (2× the BF16 path) and the 0.10 p99 our engine lands at are set by routing near-ties, not by any one rounding point; that is why a build that changes a single summation order can land on either side of the p99 limit, and why the second run kept every sum's order. And activations in float32 would cut the error only 3–4×, because the routes would still flip, only less often.由此得到两点。第一，gate 的上限（BF16 路径的 2 倍）以及我们 engine 落在的 0.10 p99，都由路由的近似平局决定，而不是由某一处舍入决定。所以只改一个求和顺序的 build 就可能落在 p99 上限的任一侧，这也是第二轮坚持保持所有求和顺序的原因。第二，即使激活改用 float32，误差也只能降 3–4 倍，因为路由仍会翻转，只是少一些。

A side finding: on this GPU with MLX 0.32.4, a float32 mx.matmul with more than one row has relative error 7.7 × 10−4 against float64, about TF32 precision; one row (GEMV) is accurate to 1.5 × 10−7. So mlx-lm after set_dtype(float32) still lands at 0.030. Fed one token at a time, so that every product is a GEMV, it agrees with our reference to 3 × 10−4 with identical top-1: the two implement the same function.一个附带发现：在这块 GPU 上用 MLX 0.32.4，多于一行的 float32 mx.matmul 相对 float64 的误差是 7.7 × 10−4，大约是 TF32 精度；只有一行（GEMV）时精确到 1.5 × 10−7。所以 mlx-lm 即使 set_dtype(float32) 之后误差仍是 0.030。改成一次喂一个 token、让每个乘积都是 GEMV 后，它和我们的 reference 只差 3 × 10−4，top-1 完全一致：两者实现的是同一个函数。

Timing on a laptop在笔记本上计时

Two things make a single number on this Mac unreliable, and both runs spent evaluations to measure them.有两件事让这台 Mac 上的单次数字不可靠，两轮都专门花了评测次数去量它们。

  • Machine state. After a long stretch of in-process tests, 16-row passes take 56–62 ms instead of 50–53 for the same engine; 15 idle minutes clear it. The run 1 engine measured 9,394 at the start of run 2 and 8,985 two hours later. The six evaluations of the final source span 8,040–8,333.机器状态。 进程内连续测试一段时间后，同一个 engine 的 16 行 pass 会从 50–53 ms 变成 56–62 ms；空闲 15 分钟就能恢复。第一轮的 engine 在第二轮开始时测出 9,394，两小时后测出 8,985。最终源码的六次评测分布在 8,040–8,333。
  • Which prompts loop. The three repeats of a workload are different prompts, and a continuation that falls into a loop decodes 2–3× faster through copy proposals. Which ones loop is decided by last-bit numerics, so a build that changes a summation order can move the headline by 30% without changing the speed of any pass. Run 1 saw 9.5–14.2 k on one workload across numerically different builds.哪些 prompt 会进入循环。 一个 workload 的三次重复是三个不同的 prompt，续写一旦进入循环，借助 copy proposals 会快 2–3 倍。哪些会进入循环由最后几位的数值决定，所以一个改了求和顺序的 build，可能在任何 pass 都没变快的情况下让主指标变动 30%。第一轮在数值不同的 build 之间，同一个 workload 测出过 9.5–14.2 k。

The general engines were measured in their own sessions, and we do not know their machine state. Treat differences under 5% as noise until they repeat.通用 engine 是在各自的会话里测的，我们不知道当时的机器状态。5% 以内的差异，在复现之前都当作噪声。

Serving it部署

The engine is registered in mkserve as offline-c for m5max, so mkserve serve thinkingmachines/Inkling-2-Mini on an M5 Max serves it on one port behind the OpenAI (/v1/chat/completions, /v1/completions, /v1/responses), Anthropic (/v1/messages) and Ollama (/api/chat, /api/generate) APIs, with Inkling 2's reasoning, text and tool calls returned in the fields each API uses. mkserve launch claude | codex | opencode points those agents at it. It passes all twelve checks of scripts/mkserve_check.py: completions and chats, streamed and not, stop strings, four concurrent requests, a 1,630-token prompt, a request beyond the context (refused with HTTP 400) and invalid inputs.engine 已经以 offline-c 的名字注册进 mkserve 的 m5max。在 M5 Max 上执行 mkserve serve thinkingmachines/Inkling-2-Mini，就会在同一个端口上提供 OpenAI（/v1/chat/completions、/v1/completions、/v1/responses）、Anthropic（/v1/messages）和 Ollama（/api/chat、/api/generate）三种 API，Inkling 2 的推理、正文和 tool call 按各 API 约定的字段返回。mkserve launch claude | codex | opencode 可以把这些 agent 接到它上面。它通过了 scripts/mkserve_check.py 的全部 12 项检查：completion 和 chat（流式和非流式）、stop string、四个并发请求、一个 1,630-token 的 prompt、超出上下文的请求（以 HTTP 400 拒绝）、以及非法输入。

Two things surfaced on the way. Inkling 2's template takes reasoning_effort and ignores Qwen's enable_thinking, which many clients send, so mkserve now maps enable_thinking: false to effort none. And even at effort none the model reasons briefly before answering (46 tokens for "Say hello."), so a client that sets a 24-token limit gets only reasoning back.过程中发现了两件事。第一，Inkling 2 的 template 只认 reasoning_effort，不认很多 client 会发的 Qwen 风格 enable_thinking，所以 mkserve 现在把 enable_thinking: false 映射成 effort none。第二，即使 effort 是 none，模型在回答前也会先简短推理（"Say hello." 推理了 46 个 token），所以把上限设成 24 个 token 的 client 只会拿到推理内容。

Prefill预填充

The engine first prefilled a prompt the way it verifies drafts, in passes of 8 rows: 3.6 ms per prompt token, 6.3 s to the first token of a 1,630-token prompt. The kernels were built for few rows. A GEMV keeps one accumulator per row in registers and spills from 32 rows on (a 32-row pass takes 274 ms, against 47 ms for 16), and the attention kernel reads every key once per row. Prompts now go through wide passes of up to 256 rows, padded to 32, 64, 128 or 256 so only four shapes are ever compiled. The padding rows come after the real ones, so they never affect them. A wide pass runs in one of two modes.engine 最初像验证 draft 一样，用 8 行的 pass 预填充 prompt：每个 prompt token 3.6 ms，1,630-token 的 prompt 要 6.3 s 才出第一个 token。这些 kernel 是为少量行写的：GEMV 在寄存器里给每行留一个累加器，从 32 行起开始溢出（32 行的 pass 要 274 ms，16 行只要 47 ms）；attention kernel 每一行都要把所有 key 读一遍。现在 prompt 走宽 pass，每个最多 256 行，补齐到 32、64、128 或 256 行，所以只会编译这四种形状。补齐的行排在真实行之后，不会影响它们。宽 pass 有两种模式。

  • Exact, the engine's default and what the evaluator runs. These are the step's own kernels, with the GEMVs in blocks of 8 rows per simdgroup and the experts in slots of 8 pairs. Every row keeps the bits of a one-row step: the K/V of all 48 layer applications is identical to the 8-row prefill's, and eval/spec_check.py finds the online tokens equal to step-by-step greedy on 4 of 4 prompts.exact，engine 的默认值，也是 evaluator 跑的模式。用的是 step 自己的 kernel：GEMV 每个 simdgroup 处理 8 行一块，experts 每个 slot 8 个 pair。每一行都保持单行 step 的 bits：48 次层应用的 K/V 与 8 行预填充逐位相同，eval/spec_check.py 在 4 个 prompt 上都判定 online 的 token 等于逐步 greedy 的结果。
  • Fast, which mkserve serves. The experts go through MLX's gather_qmm on the stored NVFP4 / MXFP8 codes in half precision. Its layout matched our kernels' without conversion. The inputs are scaled by 2−8, because the raw products before NVFP4's outer scale (about 10−4) reach 250,000 on real text, past the half range. The dense matrices go through half GEMMs on half copies (1.3 GB more memory). Attention uses mx.fast.scaled_dot_product_attention, with the relative bias and the window as an additive mask and the per-row sink as one extra zero key.fast，mkserve 部署时用的模式。experts 走 MLX 的 gather_qmm，直接在存储的 NVFP4 / MXFP8 编码上做半精度计算，它的数据布局和我们的 kernel 一致，不需要转换。输入先乘 2−8：NVFP4 外层 scale 约 10−4，乘它之前的原始乘积在真实文本上能到 250,000，超出半精度范围。dense 矩阵用半精度副本做半精度 GEMM（多占 1.3 GB 内存）。attention 用 mx.fast.scaled_dot_product_attention：相对位置偏置和窗口写成加性 mask，每行的 sink 当作多出来的一个零 key。

In a 256-row pass at position 768, the exact mode spends 2.6 ms per prompt token. 1.84 ms of it is the experts, which are bound by fp32 multiply-adds: each pair's sums must keep the step's order, so the matrix units are out. The fast mode spends 0.68 ms: experts 0.38, dense matrices 0.06, attention and the per-row kernels (depth mixes, gates, short convolutions) 0.24. That last part, not the matrix products, is now the largest piece left to fuse.在位置 768 的一个 256 行 pass 里，exact 模式每个 prompt token 花 2.6 ms，其中 1.84 ms 是 experts。它们受 fp32 乘加吞吐限制：每个 pair 的求和必须保持 step 的顺序，所以用不上矩阵单元。fast 模式每 token 花 0.68 ms：experts 0.38，dense 矩阵 0.06，attention 和逐行 kernel（depth mix、gate、short convolution）0.24。剩下最值得融合的是最后这一块，而不是矩阵乘。

The fast mode is not step-exact: on spec_check's random prompts, 1 of 4 replies matches step greedy, and the others first differ at tokens 1, 4 and 287. It is no further from the float32 reference, though. On the reference sequence it is closer:fast 模式不是 step-exact 的：在 spec_check 的随机 prompt 上，4 个回复里只有 1 个与 step greedy 相同，其余分别在第 1、4、287 个 token 处开始不同。但它离 float32 reference 并不更远。在 reference 序列上，它反而更近：

So mkserve's registry entry sets MK_PREFILL=fast through a new env field, while the evaluator and anyone who needs replies equal to step greedy get the exact mode. mkserve's sampling (step) mode now also prefills through the engine's wide passes instead of one step() per prompt token.所以 mkserve 的注册项通过新增的 env 字段设置 MK_PREFILL=fast；evaluator，以及需要回复与 step greedy 完全一致的用户，用 exact 模式。mkserve 的 sampling（step）模式现在也用 engine 的宽 pass 预填充，不再每个 prompt token 调一次 step()。

Prefix cacheprefix cache

The K/V arrays are indexed by position, so a request that starts with the tokens of the previous one can keep them. The only state that is not by position is the conv windows, the last three inputs of four short convolutions in each of the 48 layer applications: 3.8 MB. The engine keeps a snapshot of them every 64 positions, during prefill and decode. A new request is cut back to the last snapshot inside the prefix it shares with the cached sequence and prefills only the rest.K/V 数组按位置索引，所以一个请求如果开头和上一个请求的 token 相同，就可以直接沿用。唯一不按位置存的状态是 conv window：48 次层应用里各有 4 个 short convolution，每个保留最近 3 个输入，一共 3.8 MB。engine 在预填充和解码过程中每 64 个位置给它存一份快照。新请求退回到它与缓存序列的公共前缀内最近的一个快照，只预填充剩下的部分。

  • Exact. In the exact mode the tokens equal those after a full reset in six cases: the next turn of a chat, the same prompt, a prefix of it, a prompt that diverges after 1,000 tokens, nothing shared, and a 3,000-token prompt plus its reply.精确。 exact 模式下，六种情况的 token 都与完全重置后的结果相同：对话的下一轮、同一个 prompt、它的一个前缀、1,000 token 之后分叉的 prompt、完全不共享、以及 3,000-token prompt 加上它的回复。
  • Through mkserve. A chat with a 1,452-token system prompt gets its first token after 1.60 s on turn 1 and after 0.20, 0.20 and 0.18 s on the next three, with 1,408 to 1,536 prompt tokens kept. The kept tokens are reported in each API's usage (cached_tokens, cache_read_input_tokens).通过 mkserve。 系统 prompt 为 1,452 token 的对话，第 1 轮首 token 是 1.60 s，后三轮是 0.20、0.20、0.18 s，沿用了 1,408 到 1,536 个 prompt token。沿用的 token 数在各 API 的 usage 里报告（cached_tokens、cache_read_input_tokens）。

Long context长上下文

The engine was registered with 4,096 tokens of context. A coding agent sends 10,000 to 20,000 tokens of system prompt and tool definitions before the first message, so every request from one was refused. Three things stood between the engine and a long context.engine 最初注册的上下文是 4,096 token。coding agent 在第一条消息之前就要发送 10,000 到 20,000 token 的系统 prompt 和工具定义，所以它的每个请求都会被拒绝。要支持长上下文，有三处要改。

  • Attention scores. The decode attention kernel kept one score per key in threadgroup memory, 32 KB, enough for 7,168 keys. Only 8 of the 48 layer applications attend globally; the other 40 see a 1,024-token window and never need more scores than that. The 8 global ones now keep their scores in a device buffer: the same statements, so the same bits.attention 分数。 解码用的 attention kernel 把每个 key 的分数放在 threadgroup 内存里，只有 32 KB，最多放 7,168 个 key。48 次层应用里只有 8 次是全局 attention；另外 40 次只看 1,024 token 的窗口，需要的分数不会超过这个数。那 8 次全局的现在把分数放进 device buffer：语句不变，所以 bits 也不变。
  • Log scaling. Past position 8,192 the model scales the queries of its global layers by 1 + 0.1 ln(position / 8,192). The engine had never reached such a position and did not implement it.log scaling。 位置超过 8,192 之后，模型会把全局层的 query 乘以 1 + 0.1 ln(position / 8,192)。engine 以前到不了这么远的位置，没有实现它。
  • The draft head. Its passes rewrite its whole K/V every cycle, so their cost would grow with the context. Beyond 4,104 positions it is now a ring over the most recent 4,104. That changes what is proposed, never what is returned.draft head。 它的 pass 每个 cycle 都会重写自己的整个 K/V，开销会随上下文增长。超过 4,104 个位置后，它现在是一个只覆盖最近 4,104 个位置的环形缓冲。这只改变它提议什么，不改变返回什么。

A decode step takes 13.6 ms at position 0 and 19.0 ms at position 30,000; a fast prefill pass takes 0.76 ms per token at position 4,096 and 1.10 at 30,000. An agent-sized request over the Anthropic API (19,683 tokens of system prompt and four tool definitions) took 21.7 s to its first token the first time. The next two turns read about 19,500 tokens from the prefix cache and started after 1.07 s and 0.82 s; the third was a correct tool call.一个解码 step 在位置 0 是 13.6 ms，在位置 30,000 是 19.0 ms；fast 预填充 pass 在位置 4,096 是每 token 0.76 ms，在 30,000 是 1.10 ms。通过 Anthropic API 发一个 agent 规模的请求（19,683 token 的系统 prompt 加四个工具定义），第一次到首 token 用了 21.7 s。之后两轮从 prefix cache 读了约 19,500 个 token，分别在 1.07 s 和 0.82 s 后开始输出；第三轮是一次正确的 tool call。

The gates stop at position 1,152, so long positions got their own check: float32 references of a 9,600-token and a 24,000-token text. The engine's top-1 token equals float32's at all 58 checked positions. At 24,000 tokens, past the log-scaling threshold, its median logit error is 0.105 against 0.089 for the reference's own BF16 path, inside the evaluator's 2× rule; with the log scaling left out, the median KL is 17 times higher. This is one text per length.gate 只到位置 1,152，所以长位置另外做了检查：一条 9,600 token 和一条 24,000 token 文本的 float32 reference。在检查的全部 58 个位置上，engine 的 top-1 token 都与 float32 相同。在 24,000 token 处（已过 log scaling 的阈值），它的 logit 误差中位数是 0.105，reference 自己的 BF16 路径是 0.089，在 evaluator 的 2× 规则之内；去掉 log scaling 后，KL 中位数高 17 倍。每种长度只有一条文本。

Samplingsampling

Speculation was exact only for greedy decoding, so a request with a temperature was either decoded greedily or served one token per pass. Most chat clients send a temperature. Exact draft-and-verify needs each token to be a function of its own row's logits; a sampled token usually also depends on a random number drawn in sequence. The engine makes it a function of the row again: a token is argmax(logits / T + noise), where the noise is a Gumbel variable hashed from (seed, position, token id). That is a draw from softmax(logits / T), and top_p and top_k only restrict the argmax to the tokens above a threshold.speculation 以前只对 greedy 解码是精确的，所以带 temperature 的请求要么被当成 greedy 解码，要么一个 pass 只解一个 token。而大多数聊天客户端都会发 temperature。精确的 draft-and-verify 要求每个 token 只由它所在那一行的 logits 决定；采样出的 token 通常还依赖一个按顺序抽取的随机数。engine 让它重新变成只由这一行决定：token 是 argmax(logits / T + noise)，其中 noise 是由 (seed, position, token id) 哈希出来的 Gumbel 变量。这等价于从 softmax(logits / T) 采样，top_p 和 top_k 只是把 argmax 限制在高于某个阈值的 token 里。

A row of a verify pass then draws exactly the token a one-token step draws, because the logits have the same bits and so has the noise. The draft head draws with the same noise, which keeps its tokens close to the target's. On four prompts and four settings (temperature 0.3, 0.7, 1.0 with top_p 0.95, 0.8 with top_k 40), 256 tokens each, the request path returned exactly the tokens of step-by-step sampling with the same seed in all 16 cases.这样验证 pass 的每一行抽到的 token，就和单 token step 抽到的完全相同，因为 logits 的 bits 相同，noise 也相同。draft head 用同样的 noise 抽样，所以它的 token 会贴近 target 的。在 4 个 prompt × 4 种设置（temperature 0.3、0.7、1.0 加 top_p 0.95、0.8 加 top_k 40）、每个 256 token 的测试里，请求路径返回的 token 在全部 16 种情况下都与用同一个 seed 逐步采样的结果完全相同。

The engine with all of this added (wide prefill, prefix cache, long context, sampling) was evaluated once more in full: valid, every gate at the same value as before, 8,205 µs per token on synthetic prompts and 5,173 on natural text, inside the earlier ranges.加上这些之后（宽 pass 预填充、prefix cache、长上下文、sampling），engine 又完整评测了一次：valid，每项 gate 的数值都与之前相同，synthetic 是每 token 8,205 µs，自然文本是 5,173 µs，都在之前的范围内。

Limits and next局限与下一步

  • One sequence, one machine. Requests queue behind each other. Everything here was measured on one M5 Max with 48 GB; other Apple chips run the same kernels but are untested.单序列、单台机器。 请求只能排队。这里的一切都是在一台 48 GB 的 M5 Max 上测的；其他 Apple 芯片能跑同样的 kernel，但没有测过。
  • The reference. It is float32 on one sequence, and the gates cover positions up to 1,152. Long positions were checked on two texts, outside the gates. The engine has not had the independent audit the GPU engines had.reference。 它是一条序列上的 float32，gate 只覆盖 1,152 以内的位置。长位置是在 gate 之外用两条文本检查的。这个 engine 还没有做过 GPU engine 那样的独立审计。
  • Sampling is exact against the engine's own sampler, not against another implementation's random numbers. On hard prose at high temperature it is no faster than one token per pass.sampling 的“精确”是相对 engine 自己的 sampler，而不是相对别的实现的随机数。在高 temperature 的难散文上，它并不比每 pass 一个 token 快。

  • The draft head. On prose the head's first token is right 60–70% of the time, and that, not the passes, now limits the headline.draft head。 在散文上 head 的首 token 只有 60–70% 是对的，现在限制主指标的是它，而不是 pass。
